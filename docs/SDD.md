# SDD: система «Путь стажёра» (AI-Buddy)

**Версия:** 1.0
**Статус:** спецификация текущего демонстрационного прототипа
**Назначение документа:** описать цели, границы, архитектуру, поведение, ограничения и проверку системы. Это as-built спецификация репозитория, а не утверждение о реальной инфраструктуре или регламентах Авито.

## 1. Назначение и область действия

«Путь стажёра» — веб-прототип AI-помощника для онбординга. Он помогает стажёру ориентироваться в демонстрационной базе знаний, задачах и чек-листе, находить людей для обращения, формировать черновики действий и фиксировать достижения.

В состав прототипа входят:

- веб-клиент для стажёра и наставника;
- REST API и потоковые ответы ассистента через Server-Sent Events (SSE);
- база данных для демонстрационного состояния и пользовательских данных;
- MCP-имитация корпоративных источников и систем заявок;
- локальная коллекция вымышленных документов и тестовых данных.

### 1.1 Цели

1. Давать ответы по доступным материалам с источниками, а при недостаточной уверенности — не выдавать догадку за факт.
2. Поддерживать самостоятельное обучение: наводящие вопросы, чек-лист и микро-задания.
3. Объяснять, к кому обратиться, и помогать подготовить сообщение или заявку, не скрывая от пользователя момент подтверждения.
4. Отделять личные чаты стажёра от данных о его прогрессе, доступных наставнику.
5. Позволять локально проверить интерфейс и основные сценарии без реальных корпоративных систем и обязательного внешнего LLM-ключа.

### 1.2 Вне области действия

- Реальная интеграция с корпоративными Jira, Confluence, Bitbucket, Mattermost и системами заявок: в репозитории используется `mock-corp`.
- Подтверждение подлинной личности или production-аутентификация: демонстрационный вход выполняется по ID тестового пользователя.
- Работа с реальными политиками, данными сотрудников, паролями, токенами или конфиденциальными документами.
- Автоматическая отправка сообщения от имени сотрудника в Mattermost.
- Production-гарантии доступности, безопасности, масштабирования и хранения данных.

Все пользователи, компании, документы и сценарии в проекте вымышленные. Их нельзя использовать как реальные регламенты.

## 2. Заинтересованные лица и роли

| Роль | Возможности прототипа | Ограничения |
|---|---|---|
| Стажёр (`intern`) | Чаты, поиск ответов, задачи, чек-лист, практика, заявки, знакомства, журнал и настройки приватности | Доступ только к собственным данным; действия требуют предусмотренного подтверждения |
| Наставник (`mentor`) | Просмотр доступного прогресса стажёров и создание задач | Не имеет доступа к чатам, сообщениям, вложениям и личным записям стажёра |
| Лид (`lead`) | Представлен в демонстрационных данных и проверках ролей | Не получает доступ к личным данным стажёра; отдельный экран лида не входит в клиентский прототип |
| Разработчик / проверяющий | Запуск стека, тестов, eval-набора и просмотр OpenAPI | Работает только с синтетическими данными |

Тестовые учётные записи: `anya` и `dima` (`intern`), `boris` (`mentor`), `maria` (`lead`). Паролей и регистрации в прототипе нет.

## 3. Контекст и границы системы

```text
Браузер
  └── React/Vite frontend
        └── /api (HTTP/JSON, SSE)
              └── FastAPI backend
                    ├── PostgreSQL — состояние и индекс документов
                    ├── Redis — подключаемое KV-хранилище
                    ├── mock-corp (MCP) — имитация корпоративных источников и действий
                    └── LLM/embeddings provider — fake или OpenAI-compatible
```

При запуске Compose веб-клиент обслуживается Nginx и проксирует `/api` в API. Vite dev-сервер использует `/api` proxy на `http://localhost:8000`. В режиме `mock` frontend обращается к локальному mock-router и не требует backend.

### 3.1 Внешние интерфейсы

| Интерфейс | Протокол / назначение |
|---|---|
| Frontend → API | HTTP REST, JSON; потоковые ответы — `text/event-stream` |
| Frontend → локальный mock | Тот же клиентский API-контракт, mock-router в браузере |
| Backend → mock-corp | MCP по HTTP в Compose или in-process в тестах |
| Backend → database | SQLAlchemy async; PostgreSQL в Compose, SQLite в тестах |
| Backend → LLM | Fake без сетевых вызовов либо OpenAI-compatible API |

Полный перечень маршрутов, схем, кодов ошибок и SSE-событий приведён в [`../API.md`](../API.md). OpenAPI доступен в запущенной системе по `/docs`.

## 4. Архитектурное решение

### 4.1 Компоненты

| Компонент | Реализация | Ответственность |
|---|---|---|
| Веб-клиент | React 19, TypeScript, Vite | Экран входа и выбора режима, чаты, UI карточек, задачи, чек-лист, практика, журнал, приватность и наставнический экран |
| API | FastAPI, Pydantic, SQLAlchemy async | Авторизация прототипа, проверка ролей и владения данными, бизнес-правила, SSE и работа с хранилищами |
| Персистентное хранилище | PostgreSQL 16; SQLite для тестов | Пользователи, профили, документы, чаты, действия и другие сущности |
| KV | Redis в Compose; memory-адаптер в тестах | Поддерживаемые приложением быстрые временные данные |
| MCP-имитация | `mcp/mock-corp` | Вымышленные Wiki, трекер, Git, доступы и другие демонстрационные инструменты |
| LLM / embeddings | Fake или OpenAI-compatible | Маршрутизация вопросов и генерация ответов; вычисление эмбеддингов |
| Демонстрационные данные | `seed/`, `prompts/` | Вымышленная wiki, роли, чек-лист и контент для сценариев |

### 4.2 Поток ответа ассистента

1. Клиент отправляет сообщение в чат и получает поток SSE.
2. Backend проверяет сессию, роль, владение чатом, лимиты и доступность привязанных данных.
3. Ассистент определяет тип запроса, применяет правила безопасности и при необходимости ищет в базе знаний или обращается к MCP-имитации.
4. Для retrieval доступ к документам применяется до поиска; результаты ранжируются гибридно (лексический и семантический сигналы с объединением рангов).
5. Ответ передаётся событиями `status`, `token`, `source` и типизированными блоками; завершение обозначается `done`. Ошибки передаются как явное событие `error`.
6. Если ответа по доступным материалам нет, ассистент должен обозначить ограничение и при необходимости подсказать человека, а не выдумывать источник.

Индексация хранит эмбеддинги как JSON и ранжирует небольшую демонстрационную коллекцию в Python. Это ограничение прототипа; данный способ не заявляется как оптимальный для production-масштаба.

### 4.3 Основные сущности

- **User / InternProfile** — тестовая роль и профиль стажёра.
- **Task / ChecklistStep / InternStep / PracticeTask** — задачи, этапы онбординга и практика.
- **Chat / Message / Attachment** — личные разговоры, сообщения, источники и вложения.
- **Document / DocChunk** — демонстрационные документы, фрагменты и поисковые данные.
- **Action / DocIssue** — черновики и результаты заявок, а также сообщения о расхождениях документов.
- **Contact / JournalEntry** — личные знакомства и записи журнала достижений.

Схема ORM расположена в `apps/api/app/models.py`; детали клиентского контракта — в `API.md`.

## 5. Функциональные требования

| ID | Требование |
|---|---|
| FR-01 | Система предоставляет список тестовых пользователей и выдаёт токен для выбранного пользователя; отдельного процесса регистрации нет. |
| FR-02 | Стажёр может создавать и просматривать собственные чаты, отправлять сообщения в guide/direct-режиме, повторять ошибочный запрос, оставлять оценку ответа и получать ответы по SSE. |
| FR-03 | Ответ по базе знаний содержит источники, когда они использованы. При недостатке доступных данных система показывает отсутствие ответа/ограничение, а не представляет предположение как факт. |
| FR-04 | Система показывает путь стажёра и чек-лист, позволяет обновлять статус шагов и создавать/закрывать микро-задания. |
| FR-05 | Система показывает задачи, синхронизируемые с MCP-имитацией. Закрытая задача доступна только для чтения; нельзя создавать в ней новый чат. |
| FR-06 | Ассистент может подготовить черновик заявки на доступ, отгул или сообщения о расхождении. Пользователь видит поля и должен явно подтвердить действие до его передачи в MCP-имитацию. |
| FR-07 | Стажёр может сохранять найденные контакты и подсказки для обращения. Система не отправляет личное сообщение за пользователя. |
| FR-08 | Стажёр может сформировать, редактировать и экспортировать журнал достижений. Удаление чата не должно удалять уже сохранённые записи журнала и контакты. |
| FR-09 | Стажёр может просматривать и менять настройки приватности, включая настройку показа тем наставнику, и удалять свои чаты. |
| FR-10 | Наставник может просматривать разрешённые сводные данные о прогрессе и создавать задачи стажёру, но не читать его чаты и сообщения. |
| FR-11 | Система поддерживает демонстрационные уведомления, статусы и переходы по связанным экранам. |
| FR-12 | Вложения ограничены типами и размером, установленными API-контрактом; интерфейс должен предупреждать не прикладывать секреты. |

## 6. Требования к приватности и безопасности

1. Backend является источником истины для проверки ролей и принадлежности данных; скрытие элементов только на UI не является контролем доступа.
2. Чаты, сообщения, вложения, контакты, журнал, практика, приватность и заявки доступны только роли `intern` и только владельцу данных.
3. Запрос наставника или лида к личному содержимому стажёра отклоняется `403`; обращение к чужому объекту не должно раскрывать его существование и возвращает `404` согласно API-контракту.
4. Наставнику доступны только явно предусмотренные сводки прогресса и рабочие задачи; включение тем чатов в такой обзор регулируется настройкой приватности.
5. Действия с побочным эффектом не выполняются при одном лишь предложении ассистента: перед MCP-вызовом требуется явное подтверждение пользователя.
6. Документы, вложения и содержимое запросов считаются недоверенным вводом. Инструкции, найденные внутри документа, не должны переопределять системные правила.
7. Ограничения запросов, типов и размера вложений, обработка ошибок и SSE описаны в [`../API.md`](../API.md).
8. Демо-вход и значения `dev-only` не подходят для production. Для реального развертывания потребуются промышленная аутентификация, секреты вне репозитория, модель угроз, аудит доступа и отдельная проверка безопасности.

## 7. Нефункциональные требования и ограничения

- **Демонстрируемость:** базовый сценарий запускается одной командой Docker Compose и работает с fake LLM без внешнего ключа.
- **Локальная разработка:** frontend может работать отдельно в mock-режиме; API-тесты используют SQLite и in-process MCP-имитацию.
- **Контракт:** клиент и backend используют JSON-схемы; потоковый ответ передаётся как SSE.
- **Конфигурируемость:** провайдер LLM и адрес API настраиваются окружением; секреты не помещаются во frontend-переменные `VITE_*`.
- **Масштаб:** поисковый корпус и реализация индекса ориентированы на прототип, не на большой production-корпус.
- **Достоверность данных:** сиды полностью демонстрационные; ответы и примеры не являются рабочими политиками компании.

## 8. Развёртывание и конфигурация

### 8.1 Docker Compose

`docker-compose.yml` запускает:

| Сервис | Назначение |
|---|---|
| `db` | PostgreSQL 16 с образом pgvector |
| `redis` | Redis 7 |
| `mock-corp` | HTTP MCP-имитация |
| `api` | FastAPI на порту 8000 |
| `web` | Собранный frontend за Nginx на порту 5173 |

Схема БД мигрируется при запуске API; сид загружается, если база ещё не заполнена. PostgreSQL и вложения используют Docker volumes.

### 8.2 Важные параметры окружения

| Переменная | Назначение |
|---|---|
| `DATABASE_URL`, `REDIS_URL` | Подключения к хранилищам |
| `LLM_PROVIDER` | `fake` или `openai_compatible` |
| `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` | Параметры внешнего LLM-провайдера |
| `EMBEDDINGS_PROVIDER`, `EMBEDDINGS_MODEL` | Провайдер и модель эмбеддингов |
| `MCP_URL` | `inprocess` или URL MCP-имитации |
| `DEV_MODE` | Доступность dev-ручек |
| `JWT_SECRET` | Секрет подписи токенов; значение примера предназначено только для разработки |

Полный перечень и пример без производственных секретов находятся в [`../.env.example`](../.env.example).

## 9. Проверка и критерии приёмки

### 9.1 Автоматические проверки

Backend, из `apps/api`:

```bash
python -m pip install -e ".[dev]"
python -m pytest -q
python -m pytest -q --cov=app --cov-report=term --cov-report=xml:coverage.xml --cov-fail-under=80
python -m ruff check app tests
```

Frontend, из `intern-path`:

```bash
npm ci
npm run typecheck
npm run test:run
npm run test:coverage
npm run build
```

### 9.2 Критерии приёмки прототипа

- Compose поднимает web, API, БД и MCP-имитацию; интерфейс доступен на `http://localhost:5173`.
- Тестовые аккаунты доступны, а роли получают соответствующие интерфейсы.
- Вопрос по демонстрационной wiki возвращает ответ с источником; недоступный материал не раскрывается.
- Сообщение ассистента отображается из SSE-потока без блокировки остального интерфейса.
- Заявка не отправляется до явного подтверждения; запрос глобального доступа отклоняется без заявки.
- Удаление чата не удаляет сохранённые записи журнала и контакты.
- Наставник видит разрешённый прогресс, но не может прочитать чат стажёра.
- Backend- и frontend-тесты проходят; отчёты покрытия показывают более 80% по соответствующим наборам исходников.

### 9.3 Снимок проверки

При последней локальной проверке этого снимка репозитория прошло 130 backend-тестов с общим покрытием 94,67% и 85 frontend-тестов с покрытием строк 89,97% (statements 89,10%, branches 82,18%, functions 83,60%). Эти цифры относятся к конкретному запуску, а не заменяют повторную проверку после изменений.

Frontend HTML/LCOV-отчёт сохранён в `intern-path/coverage/`. Backend XML формируется командой покрытия и публикуется CI как артефакт `coverage-backend`.
