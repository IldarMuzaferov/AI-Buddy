# Фронтенд «Путь стажёра» (AI-Buddy)

Документация по клиентскому приложению, расположенному в каталоге `intern-path/`.

## 1. Назначение приложения

«Путь стажёра» — веб-интерфейс AI-помощника для онбординга. Фронтенд позволяет стажёру задавать вопросы, получать ответы с источниками и структурированными карточками, проходить чек-лист, выполнять микро-задания, работать с задачами и вести журнал достижений. Для наставника предусмотрен отдельный экран с информацией о стажёрах и созданием задач.

Проект поддерживает два источника данных:

- **Мок-режим (`mock`)** — локальный адаптер API и демонстрационные данные. Изменения мок-данных сохраняются в `localStorage` браузера.
- **Серверный режим (`server`)** — запросы к HTTP API бэкенда.

Интерфейс использует единые Zod-контракты для обоих режимов.

## 2. Технологии и требования

### Основной стек

- React 19 и React DOM;
- TypeScript в строгом режиме;
- Vite 8 — dev-сервер и сборка;
- TanStack Query — загрузка данных, кеширование, мутации и повторная актуализация;
- Zustand — состояние сеанса, навигация и поток ответа ассистента;
- Zod — проверка ответов API во время выполнения;
- `react-markdown` — отображение Markdown в сообщениях ассистента;
- `pdf-lib` и `@pdf-lib/fontkit` — формирование PDF-экспорта журнала;
- Vitest, jsdom и React Testing Library — тестирование.

### Требования к окружению

- Node.js `>=22.12.0`;
- npm (в репозитории зафиксирован `package-lock.json`).

## 3. Быстрый запуск

Перейдите в каталог фронтенда:

```bash
cd intern-path
```

Установите зависимости и запустите Vite:

```bash
npm ci
npm run dev
```

Откройте адрес, который Vite напечатает в терминале. Стандартный адрес — `http://localhost:5173`.

По умолчанию приложение работает в мок-режиме, если переменная `VITE_API_MODE` не установлена в `server`.

### Полезные команды

| Команда | Назначение |
|---|---|
| `npm run dev` | Запуск локального dev-сервера Vite |
| `npm run build` | Проверка TypeScript и production-сборка |
| `npm run preview` | Локальный просмотр production-сборки |
| `npm run typecheck` | Проверка типов TypeScript без сборки |
| `npm test` | Запуск Vitest в watch-режиме |
| `npm run test:run` | Однократный запуск всех тестов |
| `npm run format` | Форматирование `src`, `vite.config.ts`, `index.html` и `README.md` через Prettier |

Production-артефакты создаются в `dist/`.

## 4. Настройка окружения и подключение API

Пример переменных находится в `.env.example`. Для локальных настроек создайте `.env.local` в каталоге `intern-path`.

```dotenv
# mock | server
VITE_API_MODE=mock

# Целевой адрес для Vite proxy /api
API_PROXY_TARGET=http://localhost:8000

# Необязательно: полный базовый URL API, если используется отдельный API-хост
# VITE_API_BASE_URL=http://localhost:8000/api
```

### Мок-режим

```dotenv
VITE_API_MODE=mock
```

В этом режиме `createTransport` динамически вызывает `src/shared/api/mock/router.ts`. Мок-адаптер обрабатывает API-пути внутри браузерного приложения, используя демонстрационные данные из `mock/prototype-data.json` и состояние из `mock/data.ts`.

Изменения мок-данных сохраняются в `localStorage`. Для восстановления исходного демо-набора используйте действие сброса демо в служебной панели, если оно доступно для выбранного пользователя.

### Серверный режим

```dotenv
VITE_API_MODE=server
API_PROXY_TARGET=http://localhost:8000
```

1. Запустите API-сервер на `http://localhost:8000` (или укажите другой адрес в `API_PROXY_TARGET`).
2. Выберите «Локальный сервер» на экране входа либо в меню профиля.
3. Выйдите из текущего сеанса и войдите снова, если приложение попросит это сделать.

В `vite.config.ts` настроен proxy: запросы с префиксом `/api` перенаправляются на `API_PROXY_TARGET`. В `preview` используется та же настройка proxy.

`VITE_API_BASE_URL` задаёт базовый URL непосредственно в HTTP-транспорте. Если переменная не задана, используется `/api`. При использовании отдельного API-хоста настройте CORS на сервере.

> Переменные с префиксом `VITE_` встраиваются в клиентскую сборку. Не помещайте в них секреты, приватные ключи или серверные токены.

### Переключение режима

Переключатель API находится на экране входа и в настройках профиля. При смене режима активный токен и пользователь сбрасываются; кеш TanStack Query очищается. Режим API сохраняется в Zustand persist под ключом `intern-path-session-v1`.

## 5. Пользовательские роли и экраны

Список доступных тестовых пользователей загружается через `GET /auth/users`. Доступность экранов определяется ролью профиля, полученного после входа.

### Стажёр (`intern`)

- **Главная / Новый чат** — приветственный экран, поле вопроса, примеры запросов, блок «На чём остановились», следующий шаг, путь стажёра, задачи на сегодня, чек-лист и панель микро-заданий.
- **Чат** — история сообщений, потоковый ответ ассистента, источники, карточки людей, действия, конфликты документов, практика, следующий шаг и обратная связь по ответу. Можно переименовать чат, включить его в журнал и удалить чат с вложениями после подтверждения.
- **Задачи** — список задач из трекера и отдельная страница задачи с относящимися к ней чатами. Для незакрытой задачи можно создать новый чат.
- **Знакомства** — сохранённые контакты, поиск, добавление, редактирование и удаление записей.
- **Журнал достижений** — ручное добавление и редактирование записей, предложения собрать записи из чатов, выбор записей, управление экспортом и доступом наставника, экспорт в PDF.
- **Приватность** — описание доступа к данным, матрица видимости, настройка показа темы наставнику, удаление чатов и журнал доступа.
- **Заявки** — просмотр заявок и фильтрация по типу. Карточки заявки позволяют редактировать черновик, подтверждать или отменять его; для ожидающих действий может быть доступно напоминание.
- **Служебная панель** — состояние API и инструменты диагностики/демо, если они доступны на сервере.

История чатов и папки задач находятся в боковой панели. Чат можно удалить прямо из списка истории, не открывая его; перед удалением показывается подтверждение.

### Наставник (`mentor`)

Экран «Мои стажёры» показывает доступную наставнику сводку по стажёрам: этап и день онбординга, прогресс чек-листа, задачи, заявки, отгулы, проблемы с документами, подсказки для поддержки и записи журнала, которыми поделились. Наставник может создавать задачу стажёру.

Доступ наставника к чатам ограничен серверной политикой. Интерфейс содержит проверку ответа API на запрос списка чатов и показывает отказ `403`, если доступ запрещён.

### Лид (`lead`)

Для роли `lead` отдельный экран в текущем интерфейсе не реализован. В приложении показывается сообщение «Экран лида не предусмотрен».

## 6. Работа AI-помощника

Компоненты ассистента находятся в `src/features/assistant/`.

### Отправка и поток ответа

`useAssistant.ts` управляет процессом отправки:

1. Создаёт `AbortController` и блокирует повторную отправку, пока запрос выполняется.
2. Если чат ещё не существует, создаёт его через `POST /chats`.
3. Переводит пользователя на страницу нового чата.
4. Вызывает `POST /chats/{id}/messages`.
5. Получает Server-Sent Events (SSE) через Fetch-транспорт.
6. После завершения или ошибки обновляет кеш запросов.

Для запроса генерируется `Idempotency-Key` (UUID). Поток отменяется при смене сеанса/режима API или очистке состояния ассистента.

Транспорт читает `text/event-stream`, разбирает события `event` и `data`, проверяет данные события через Zod-схемы и передаёт их компонентам.

Поддерживаемые типы событий и блоков описаны в `src/shared/api/contracts.ts` и `API.md`: статус поиска, текстовые токены, источники, карточка человека, черновик действия, конфликт документов, микро-практика, следующий шаг, уведомление, ошибка и завершение потока.

### Отображение ответа

`src/widgets/conversation/MessageContent.tsx` отображает:

- пользовательские и AI-сообщения;
- Markdown-текст;
- этапы поиска;
- ссылки на источники;
- карточки людей и сохранение контактов;
- карточки заявок/действий;
- расхождения между документами;
- микро-задания и следующие шаги;
- обратную связь «Помогло / Не помогло» и повтор после ошибки.

В текущем `Composer` нет элемента выбора/прикрепления файла. При этом API-клиент содержит метод `chats.attach`, а модель сообщения и отображение сообщения умеют работать с уже существующими вложениями.

## 7. Чек-лист, микро-задания и прогресс

Реализация находится в `src/features/checklist/Practice.tsx`.

- Чек-лист загружается через `GET /checklist`.
- Статусы шагов: `todo`, `in_progress`, `done`, `hidden`.
- Изменение статуса отправляется через `PATCH /checklist/{step_id}`.
- Для шагов с практикой доступна генерация заданий через `POST /checklist/{step_id}/practice`.
- Список микро-заданий загружается через `GET /practice`.
- Статус микро-задания меняется через `PATCH /practice/{id}`; варианты — `open` и `done`.

Прогресс и подписи этапов поступают из API главной страницы (`GET /home`). На экране наставника отдельная сводка прогресса приходит из `GET /mentor/interns`.

При добавлении или изменении серверных данных `useUpdate()` инвалидирует кеш запросов текущего backend/token scope. Это вызывает повторную загрузку соответствующих данных TanStack Query.

## 9. Навигация и состояние приложения

В приложении нет отдельной библиотеки URL-маршрутизации. Текущая страница хранится в Zustand store `src/shared/ui/navigation.ts` как объект `route`; переходы выполняются вызовом `go(...)`.

Типы маршрутов:

- страницы без параметров: `home`, `contacts`, `journal`, `privacy`, `mentor`, `tools`, `actions`, `tasks`;
- страницы с идентификатором: `chat` и `task`.

Основное серверное состояние (профиль, чаты, задачи, журнал и т. п.) хранится в кеше TanStack Query. Локальное UI-состояние (открытые диалоги, выбранный фильтр, поля формы) хранится в React state компонентов. Сеанс и режим backend хранятся в Zustand.

Ключи запросов включают режим backend и токен. Это разделяет кеши разных сеансов. После мутаций `useUpdate` инвалидирует запросы текущего сеанса.

## 10. API-клиент и обработка ошибок

### Где описаны запросы

Все методы API собраны в `src/shared/api/endpoints.ts`. Подробные форматы запросов, ответов, ролей и SSE-событий находятся в [`API.md`](./API.md).

Основные группы методов:

| Группа | Назначение |
|---|---|
| `auth` | Список пользователей, вход, профиль, подтверждение первого входа |
| `home` | Данные главной страницы |
| `checklist`, `practice` | Чек-лист и микро-задания |
| `notifications` | Получение и прочтение уведомлений |
| `chats` | История чатов, создание, изменение, удаление, сообщения, вложения, обратная связь и SSE |
| `tasks` | Список задач и карточка задачи |
| `actions` | Черновики заявок, изменение, подтверждение, отмена и напоминания |
| `contacts` | Поиск, создание, редактирование и удаление контактов |
| `journal` | Записи, предложения из чатов, черновик и PDF-экспорт |
| `privacy` | Настройки приватности, сведения о доступе, удаление чатов |
| `mentor` | Список стажёров и создание задачи |
| `system` | Health, флаги, события, поиск знаний и метрики |
| `dev` | Демонстрационные и диагностические операции dev-режима |

### Формат запросов

- JSON-запросы отправляются с `Content-Type: application/json`.
- Для запросов с файлом используется `FormData` (`multipart/form-data`); браузер сам устанавливает boundary.
- При наличии токена транспорт добавляет `Authorization: Bearer <token>`.
- Для сообщений ассистенту передаётся `Idempotency-Key`.
- Запросы поддерживают `AbortSignal`.
- Ответы JSON проверяются схемой Zod соответствующего endpoint.

### Ошибки

Транспорт преобразует сетевые и HTTP-ошибки в `ApiError` с полями `status`, `code` и сообщением. Ошибка сети получает статус `0`, ошибка несовпадения ответа с контрактом — `502` и код `invalid_response`. Компоненты выводят ошибки через общий компонент `ErrorText`.

Если запрос профиля `GET /me` завершается `401`, приложение очищает кеш и завершает сеанс.

Тесты находятся в `tests/` и запускаются в `jsdom`.

## 13. Сборка и запуск в Docker

В каталоге фронтенда есть `Dockerfile` и `nginx.conf`.

Dockerfile выполняет multi-stage сборку:

1. На этапе Node 22 устанавливает зависимости через `npm ci` и запускает `npm run build`.
2. На этапе Nginx копирует `dist/` в каталог статических файлов и использует `nginx.conf`.

Nginx:

- отдаёт статические файлы фронтенда;
- перенаправляет неизвестные frontend-пути на `index.html`;
- проксирует `/api` на сервис `api:8000`;
- отключает proxy buffering для потоковых ответов и задаёт увеличенный timeout для SSE.

Сборку можно выполнить из каталога `intern-path`:

```bash
docker build -t intern-path-frontend .
docker run --rm -p 8080:80 intern-path-frontend
```

Для работы API в Docker-сети должен быть доступен сервис с именем `api` и портом `8000` либо необходимо скорректировать upstream в `nginx.conf` под инфраструктуру развёртывания.
